## Gap-close correction (adversarial-verification defect closed)

> **Superseded claim (kept visible):** the original evidence below said the new
> `/bots/interrupt` route "issues `StopTask`" and the panel "POSTs
> `/bots/interrupt {taskId, agentId, swarmId}`" for the selected agent. **The
> interrupt could never succeed.** `AgentDetailPanel` sends `selectedAgent.id`,
> which is a **claude-flow swarm `agent_id`** — a disjoint minted namespace from
> the **Management-API `task_id`** the chain `StopTask` →
> `ManagementApiClient::stop_task` requires (`DELETE /v1/tasks/{task_id}`).
> Passing the swarm agent_id straight through issued `DELETE /v1/tasks/<swarm
> agent_id>`, which the Management API 404s every time; and because
> `CANARY-VC-D2-STEER` is observed only on the SUCCESS arm, a normal interrupt
> could **structurally never fire it**. The component test proved only that the
> panel *issued the POST*, not that the POST resolved to a real stop.

**Primary fix (server-side id resolution).** A new orchestrator message
`InterruptAgentTask` (`src/actors/task_orchestrator_actor.rs`) resolves the
incoming id — a `task_id` OR a swarm `agent_id` — to a concrete `task_id` before
the stop:
1. fast path — the id is a known `task_id` in the orchestrator's `active_tasks`
   registry (e.g. a task this orchestrator created; `spawn_agent_hybrid` mints
   `swarm_id = task_response.task_id`);
2. else — consult the live Management-API task list and take the task whose
   `task_id == id`, else the task whose `agent` field carries the id;
3. else — **error**, never a blind stop of an unrelated task.

`interrupt_task` (`src/handlers/bots_handler.rs`) now sends `InterruptAgentTask`,
observes `CANARY-VC-D2-STEER` on the *resolved* success, and returns both the
resolved `taskId` and the `requestedId`. The client payload is unchanged (the
resolution is server-authoritative), so the existing interrupt component test
still holds.

  (`src/handlers/bots_handler.rs::submit_task`, mounted at

  the swarm through the same `TaskOrchestratorActor` `CreateTask` transport the

  `src/handlers/bots_handler.rs::interrupt_task` (mounted alongside submit-task)

  `/bots/interrupt {taskId, agentId, swarmId}`; the `AgentDetailPanel.interrupt`
  vitest asserts the mounted panel invokes `POST /bots/interrupt` for the
  selected agent — the falsification's "invoked from a mounted panel" clause,
  proven at the component level.
- A `/bots/task-status/{id}` route (via `GetTaskStatus`) backs the panel's
  post-submit poll so it reads real status rather than 404-ing.
- Canary seed: `CANARY_D2_STEER` added to `P1_CANARIES`
  (`src/services/liveness_harness.rs`), so `GET /api/canary/status` carries it
  (standing, P1) from boot.

## Final correction (P2 — D2-interrupt final close), 2026-07-08T15:35Z

> **Superseded claim (kept visible):** the P1 correction above resolved the
> interrupt "against the live task list: a direct `task_id` hit first, then the
> task whose `agent` field carries the id." **That second join can never fire for
> an MCP-sourced id.** A re-verifier traced it end to end: `TaskInfo.agent` only
> ever carries a **role label** ("coder"/"researcher"/…) — every in-repo
> `CreateTask` call site passes a role, never a claude-flow agent id — so
> `t.agent == id` cannot match a claude-flow swarm `agent_id`. The earlier
> integration test only passed because its fake **fabricated** the join, stuffing
> the swarm agent_id into the `agent` field. The real join was missing.

**The real join (end to end).** A task created for a claude-flow agent now carries
an explicit, additive key, `claude_flow_agent_id`, distinct from the role label:

- **agentbox** (`management-api/routes/tasks.js`, `utils/process-manager.js`, own
  repo, branch `gap-close/2026-07`, commit `9ebff75…`): create-task accepts an
  OPTIONAL `claude_flow_agent_id`, `ProcessManager.spawnTask` persists it on the
  task record, and `getTaskStatus` / `getActiveTasks` echo it as
  `claudeFlowAgentId` (added to the fastify response schemas, or fastify strips
  it).
- **VisionClaw wire** (`services/management_api_client.rs`):
  `create_task_with_context` / `create_task` carry `claude_flow_agent_id`
  (snake_case body key); `TaskInfo` and `TaskStatus` gain
  `claude_flow_agent_id: Option<String>` (camelCase `claudeFlowAgentId`,
  `#[serde(default)]`).
- **VisionClaw transport** (`actors/task_orchestrator_actor.rs`): `CreateTask`
  gains `claude_flow_agent_id: Option<String>`; the interrupt resolver gains a
  **third branch — `t.claude_flow_agent_id == id`, placed BEFORE any fallback**,
  and the `t.agent == id` fallback is **removed** (a role label equal to an agent
  id was a false-positive hazard that would stop an unrelated task).
- **Honest producer boundary.** All four in-repo `CreateTask` call sites
  (`bots_handler.rs` hive-init / spawn-hybrid / settings / steer;
  `voice_interface_actor.rs`) pass `None` — none of them genuinely knows a
  claude-flow swarm agent_id at create time (`spawn_agent_hybrid` mints
  `swarm_id = task_response.task_id`, so its agent is already resolvable by the
  task_id branch). The join **mechanism** is integrated and proven; a
  claude-flow-native producer that knows the swarm agent_id at create time
  populates branch 3. Nothing is fabricated to make the join appear populated.

**Capability boundary (the honest statement).**

- **Interruptible — task-registry-provenance agents.** When an agent's id resolves
  to a Management-API task (directly as a `task_id`, or via the
  `claude_flow_agent_id` join), the interrupt lands as a real
  `DELETE /v1/tasks/{resolved}` and `CANARY-VC-D2-STEER` can fire. Proven end to
  end (create carrying the join key → agentbox echo → resolver branch 3 → DELETE
  on the resolved task_id, never on the raw swarm agent_id) by
  `claude_flow_agent_id_join_resolves_to_task_id_and_issues_stop`.
- **Disclosed-not-interruptible — external MCP-native agents.** The MCP TCP
  surface (`src/utils/mcp_tcp_client.rs`) exposes only `agent_list`,
  `swarm_status`, `server_info`, `initialize` and the generic `tools/call`
  wrapper — **there is NO terminate/stop/kill verb**. So a claude-flow agent that
  exists only in the MCP `agent_list` (no backing Management-API task) genuinely
  cannot be stopped from this codebase. The resolver returns the distinct
  `InterruptError::Unresolved`; `interrupt_task` maps it to **HTTP 422**
  (`resolution:"unresolved"`, `interruptible:false`) — which the client does not
  retry — and `AgentDetailPanel` discloses a disabled explanatory state
  ("Externally spawned — not interruptible from here") on the first failure,
  instead of a dead retrying button.

**Tier: `integrated` (desktop) for the registry path, boundary stated.** The join
is proven against a real local HTTP server mirroring the Management-API `/v1/tasks`
contract; the live fire against a running agentbox stays `pending-live-session`
per the wave discipline. The external-MCP arm is a disclosed, unit-proven boundary,
not a gap.

**Falsification (P2) → met.** *This close is falsified if:* (a) the MCP client
still lacks a terminate verb yet the code claims MCP-native agents are stoppable —
**met:** they are explicitly disclosed as not interruptible, citing
`mcp_tcp_client.rs`; (b) `t.agent == id` still matches a role label — **met:**
removed, and guarded by `role_label_is_never_a_false_match`; (c) the resolver has
no `claude_flow_agent_id` branch, or it sits after a fallback — **met:** branch 3
is first after the direct task_id hit; (d) the fake fabricates the join — **met:**
the fake echoes `claudeFlowAgentId` ONLY when the create carried it, asserted via
the recorded create body; (e) the client leaves a dead retrying button — **met:**
distinct 422 → terminal disabled disclosure, `AgentDetailPanel.notInterruptible`
