## Falsification (PRD-023 WP-9, M1 clause)

*"WP-9 is falsified if the Godot HUD still carries no identity … control while `graph_scene.gd:431` holds the DID …"* — before: `avatar.gd` wrote only the self-reported `display_name` to the nameplate and the DID sat unused in metadata. After: the DID is rendered on a dedicated badge with a verified/unverified visual, sourced from the same meta.

Invariant 2 (DDD): *identity is verified before trust.* The badge defaults to **unverified** (amber, "?") for a presence peer — the server-vouched roster DID is **not** client-trusted on presentation. It reads verified only when `set_verified(true)` is called after the Schnorr check. No badge fabricates a "verified" state.

## What landed

### 1. Human-peer avatar (`scenes/Avatar.tscn`, `scripts/avatar.gd`)
- New `Head/DidBadge` billboarded `Label3D` below the nameplate.
- `set_identity(display_name, did, verified)` — sets the nameplate and the DID badge (short-DID `…last8` of the pubkey hex). `set_verified(bool)` flips the state.
- Verified → check mark + `Color(0.75,1.0,0.82)`; unverified → "?" + `Color(1.0,0.72,0.28)` (amber). An empty DID renders the literal `unverified` — an honest absence, never a fabricated id.
- The badge drops with the nameplate at LOD Medium (`_set_label_visibility`), so distance never leaves a floating label.
- `graph_scene.gd:_on_avatar_joined` now calls `set_identity(display_name, did, false)` — the DID that reached the meta is rendered, unverified until the client checks it.

- The geometric agent embodiment carries the same badge semantics (`set_identity` / `set_verified`, `_short_did` `…last8`, verified/unverified colour), pooled as the avatar's own `Label3D`.
